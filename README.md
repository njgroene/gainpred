# gainpred

Code, protocol, logs and paper sources for

> **Is This Round Worth Running? Steering Compositional Self-Improvement from a Model's Own Answers**
> Nikolaj Groeneweg, [Nimble Lab](https://nimblelab.ai), 2026.

The paper builds on [Shin et al. (2026), *Compositional Self-Improvement: Promises and Pitfalls*](https://arxiv.org/abs/2611.00452).
In compositional self-improvement a model splits a hard problem into easier
ones it already solves, composes their answers, and trains on the result. A
round of this can help the model, do nothing, or make it worse. We ask
whether the model can tell which, and steer the loop, from its own answers
alone: no correct answers to the hard problems and no hand-written filter.

## What the paper shows

Everything is on multi-digit addition with a 14M-parameter Transformer
trained from scratch.

- **Two quantities measured before a round, without correct answers.**
  *Novelty* is how often the composed answer (the teacher) differs from the
  model's direct answer (the student); it bounds how much a round can change
  the model. The *confirmed share* is how often a second way of splitting the
  problem gives the same answer; it bounds the teacher's accuracy from below.
- **A rule fixed before evaluation predicts single rounds.** It predicts
  whether a round pays off, does nothing, or does harm in 96.5% of 258 cases
  and flags every harmful round, at about 8% of a round's compute.
- **The same two quantities carry a loop from 8 to 39 digits.** Four arms add
  one ingredient at a time from the same starting models:

  | The model trains on | Result on three starting models |
  | --- | --- |
  | Its direct answers | Learns nothing |
  | Composed answers, unfiltered | Learns the composition together with its carry error |
  | Answers on which two splits agree | Reaches 39 digits on all three |
  | The same, skipping lengths with novelty under 2% | Same accuracy, about half the compute |

## What is fixed in advance, and where to check it

The single-round prediction rule, the rule that scores outcomes, and the pass
mark were frozen before the evaluation runs.

- The frozen state is the git tag **`stage1-freeze`**.
- **`docs/protocol.md`** is the protocol. Every change after the freeze is a
  dated, numbered amendment at its end (31 so far), with its reason.
- **`docs/ladder_spec.md`** is the specification of the 8-to-39-digit ladder,
  recorded as amendment 29 before any of its code was written. The ladder is
  exploratory: its rules were fixed in advance, but no outcome was predicted.
- Appendix A of the paper lists, result by result, what was fixed when.

Every run we launched is logged here, including runs that failed and
experiments the paper does not report (a second task, an earlier version of
the loop). See [Beyond the paper](#beyond-the-paper).

## Layout

| Path | Contents |
| --- | --- |
| `src/gainpred/` | Model, training, teachers and checks; the experiment drivers; the generators that turn logs into the paper's numbers, tables and figures |
| `tests/` | Test suite, including tests that pin the paper's headline numbers to the logs |
| `docs/` | `protocol.md` (protocol and amendments), `ladder_spec.md`, `runbook.md` (how the work was run) |
| `results/` | Logs of every run and the reports generated from them; `results/ladder/` holds the ladder's logs, per-length and per-round CSV files, and the meaning of every ladder number (`macros.md`) |
| `paper/` | LaTeX sources; `paper/generated/` holds the generated numbers, tables and figures |
| `modal_app.py` | Entry points for the GPU runs on [Modal](https://modal.com) |
| `scripts/` | One-off analysis scripts |

Not in the repository: the datasets (regenerated from seeds, see below) and
the model checkpoints (too large; the logs of every training run are here).

## Reproducing the numbers from the logs

No GPU is needed for this. You need Python 3.12 or later and
[uv](https://docs.astral.sh/uv/).

```sh
uv sync                                  # install
uv run pytest -q                         # run the tests

# Datasets are not in git; they are regenerated byte for byte from fixed seeds.
uv run python -m gainpred.data           # addition      -> data/addition/
uv run python -m gainpred.run_data       # second task   -> data/longest_run/
uv run python -m gainpred.ladder data    # ladder tests  -> data/ladder/

# Regenerate what the paper includes, from the logs in results/.
uv run python -m gainpred.writeup        # single-round study (Sections 3 and 4)
uv run python -m gainpred.ladder_paper   # the ladder (Section 5)
```

The generators write to `paper/generated/` and `results/`. Files there are
never edited by hand: every number in the paper is a macro defined in
`paper/generated/numbers*.tex`, so `git diff` after regenerating shows
whether anything moved.

## Building the paper

```sh
cd paper
make            # tectonic
make latexmk    # or a full TeX installation
```

The supplementary material is part of the same PDF, after the appendices.

## Re-running the experiments

The runs used one A10G GPU on Modal. `modal_app.py` defines the functions,
`src/gainpred/launch.py` and `python -m gainpred.ladder` launch and fetch
them, and `docs/runbook.md` describes the procedure, the budget rules and
the stop conditions. All three ladder seeds together cost about $28 of GPU
time; `results/README.md` tracks the spending of the earlier study.

## Beyond the paper

The repository holds more than the paper reports. The protocol explains each
item and why it was run.

- **A second task (longest run of a repeated symbol)**, including a case in
  which a teacher that was right about every answer it kept still harmed the
  student by leaving a class of problems out of training.
- **An earlier loop over 16 to 39 digits** (`results/pilot/`). It started
  from a model taught with the hand-written filter and trained on every
  length regardless of its checks. The ladder replaced it; the 2% novelty
  threshold of the ladder's fourth arm was chosen on its logs.
- **Rounds steered by the checks with rehearsal**, an earlier form of the
  fourth arm.

## Use of AI

Large language models and coding assistants wrote much of the experiment and
plotting code, orchestrated runs, and turned logs into tables and figures,
under the rules in `docs/runbook.md`. The author verified the hypotheses,
designs, code and numerical results and is responsible for them.
